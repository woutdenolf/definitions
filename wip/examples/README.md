# NXDS examples, one per phase of the proposal

Each phase folder contains what an **author writes** at that phase, and what
**`nxds_tools` generates** from it (always under `generated/`). The demo is the
absorption measurement of the proposal (§5): `mu` measured at each `energy` of a
monochromator, for `nE` energies, plus a counter base class.

| Folder | Written by the author | Generated by `nxds_tools` |
|---|---|---|
| `today/` | `NXdemo_today.nxdl.xml`, `NXdemo_counter_today.nxdl.xml` | nothing: there is no compiler today |
| `phase0/` | `NXdemo_phase0.nxdl.xml`, `NXdemo_counter_phase0.nxdl.xml` (unchanged NXDL) | `source/*.nxds.yaml` (translated source form, with `via`/`provisional`), `resolved/*.json` (meaning, no documentation), `docs/*.json` (documentation texts), `report.txt` |
| `phase1/` | as phase 0; plus a data file (`demo_phase1.h5`, `demo_phase1_partial.h5`, written by `make_files.py`) | as phase 0, plus `rst/*.rst` (documentation rendered from the bundle) and the validator findings `findings*.jsonl` |
| `phase2/` | `NXdemo_phase2.nxds.yaml`, `NXdemo_counter_phase2.nxds.yaml` (NXDS, only what NXDL can express) | `resolved/*.json`, `legacy/*.nxdl.xml` (generated NXDL, not committed in the real repository), `report.txt` with the round-trip result |
| `phase3/` | `NXdemo_phase3.nxds.yaml` uses `require: at_least_one_of: [mu, fluo]`, which NXDL cannot express | `resolved/*.json` (class marked `lossy: [require]`), `legacy/*.nxdl.xml` (the constraint only in the documentation) |
| `phase4/` | the same syntax; every class is NXDS (see `phase4/README.md`) | `resolved/*.json` |

The classes resolve against the real classes of this repository (`--extra`):
`NXdemo_phase2` refines `NXentry`, `NXinstrument`, `NXmonochromator` and `NXdata`,
which are still NXDL files.

## Naming kinds covered (phase 2 onwards)

| Kind | Where |
|---|---|
| fixed `{exact: …}` (the default) | `monochromator`, `counter`, `mu`, `mode` |
| free `{any: true}` | `ENTRY`, `INSTRUMENT`, `DATA` (group), `SENSOR` |
| partial `{template: "{CHANNEL}_counts"}` | `NXdemo_counter_*`; `i0_counts` in the application definition refines it and inherits its type and units: NXDL by name-fit (T18), NXDS by writing `refines: CHANNEL_counts` |
| role `{ref: "@signal"}` | `DATA` dataset in the `NXdata` group: whatever `@signal` names must be `NX_FLOAT` |

## What to look at

- `phase0/generated/source/NXdemo_phase0.nxds.yaml`: the NXDL translated row by
  row; `via` lists the rows used, `provisional` the open decisions.
- `phase0/generated/resolved/NXdemo_phase0.json`: one member per line; the
  specialisations `NXdemo_phase0/ENTRY`, `NXdemo_phase0/ENTRY/DATA`, … list every
  member, inherited ones included (`declared_by`, `refined_by`, `refines`). A
  member the class does not change is a reference to the entry listed in full
  elsewhere (`{"ref": "NXentry/start_time", "node": "dataset"}`); a reader
  follows it without merging anything. Documentation is not in the resolved
  form: `docs` lists keys of texts in `generated/docs/<class>.json`.
- `phase2/generated/resolved/NXdemo_phase2.json` has the structure of the phase-0
  one; it differs only by the role refinement of `DATA` (and the class names,
  `via`, `provisional`). The tests of `nxds_tools` check that an NXDL class and
  the same class written in NXDS resolve to the same form
  (`test_nxdl_and_nxds_resolve_alike`).
- `phase1/generated/findings.jsonl`: exactly the two findings of the proposal
  (`MISSING` `@signal`, `RECOMMENDED` `title`); `findings_partial.jsonl`: the
  same file while it is being written (partial mode, `INCOMPLETE`).
- `phase3/generated/legacy/NXdemo_phase3.nxdl.xml`: the generated NXDL states the
  constraint in its documentation only.
